# DECISIONS（決めた業務ルール）

テーブル定義書の変更は [CHANGELOG.md](CHANGELOG.md) を見てください。
関連は、Issue #3 のコメント番号（②など）です。

最終更新：2026-11-13（MVPの範囲に合わせて見直し）

## 決定済み

| No | ルール | 決定日 | 関連 |
|---|---|---|---|
| D-01 | 注文明細には order_id・listing_id・quantity だけを持たせる。商品名・単価は 出品 → 商品マスター から取る。商品マスターを編集したら updated_date を記録し、注文日時より後に更新されていたら「商品情報が変更されています」と表示する | 10/28 | 先生のレビュー |
| D-02 | 注文が入った出品は価格を変更できない。値段を変えるときは新しく出品し直す | 11/03 | D-01 |
| D-03 | 注文はお店ごとに分ける（1注文＝1店舗）。注文明細を登録するときに、出品の店舗IDが注文の店舗IDと同じかをPHPで確認し、違っていたら ROLLBACK する | 11/03 | ⑤ |
| D-04 | 注文確定（注文・注文明細の登録、在庫を減らす、デモ支払い、カートから削除）は1つのトランザクションで行う。デモ支払いに失敗したら全部 ROLLBACK して、注文は残さない（11/13：ポイント利用を外した） | 11/03 | ④ ⑤ |
| D-05 | 受け取りは「○時まで」の締め切りだけを決める。締め切りは「閉店時間」と「注文内でいちばん早い sale_end」の早いほう。ユーザーは時刻を選ばず、注文確定時にPHPで締め切りを orders.pickup_schedule に入れる。受け取りの開始時刻は持たない。ユーザー側は「19:00まで受取可」のように表示する（11/13：30分刻みで選ぶ形をやめた） | 11/03 | [②](https://github.com/bbudootan/food-loss-graduation-project/issues/3#issuecomment-6579461412) |
| D-06 | listing.quantity は「今売れる残りの数」。注文確定時に `WHERE quantity >= 注文数` を付けて減らし、0件なら在庫不足として ROLLBACK する。未受け取りの数は注文明細から計算し、売り切れは quantity = 0 で判断する | 11/03 | ④ |
| D-07 | 注文状態の変更は 0→1（受け取り）、0→2（期限切れ）だけ。1・2からは変えない。更新は `WHERE order_status = 0` を付けて行い、更新件数が0件なら何もしない（11/13：取り消しをなくした。MVPでは 0→2 は作らない → D-23） | 11/03 | ⑤ |
| D-12 | デモ支払いなので「支払い待ち」の状態は作らない。payment_status は削除する | 11/03 | ⑤ |
| D-13 | 店舗ジャンル・店舗画像は、出店申請では入力せず、承認後に店舗情報画面で入力する。店舗情報画面はMVP対象外なので、MVPではダミーデータで入れる（11/13：定休日は D-15 で列ごと削除） | 10/29 | — |
| D-14 | 注文の取り消しはしない。orders の cancel_date・cancel_reason と、order_status の「3=取り消し」を削除する | 11/13 | MVPの範囲 |
| D-15 | 店舗に定休日はなく、毎日営業している前提にする。store.closed_days を削除する | 11/13 | MVPの範囲 |
| D-16 | MVPでは、ポイント・すごろく（苗）・レビュー・お気に入り・FAQ・お問い合わせ・店舗削除申請の機能を作らない。関係するテーブル（point_history、seedling_history、review、review_report、favorite_goods、favorite_store、faq、inquiry、delete_store_application）と列（account.point_balance・seedling_balance、orders.used_point）をテーブル定義書v4から外す。作るときは v3 から戻す | 11/13 | MVPの範囲 |
| D-17 | 決済はデモ決済（「支払う」ボタンを押すだけ）。カード番号などは保存せず、カードテーブルは作らない | 11/13 | 旧P-04 |
| D-18 | 商品カードの裏面に保存方法を表示するため、goods_master に storage_method（nvarchar(50)、NULL可）を追加する。例：冷蔵（10℃以下）、冷凍、常温 | 11/13 | ユーザー側の商品カード v5 |
| D-19 | 期限切れのとき、在庫は自動で戻さない。MVPのデモでは扱わない例外なので、ルールをシンプルにする | 11/13 | 旧P-01 |
| D-20 | MVPでは OCR（商品画像の文字の読み取り）は作らない。管理者が写真を見て、商品マスターに手で登録する | 11/13 | 旧P-03 |
| D-21 | 商品登録依頼は、店舗が写真を送るだけで申請する（手入力の依頼はなし）。管理者が写真を見て商品マスターに登録する。写真から登録できない依頼は差し戻さず、対応状態を「2=登録しない」にする | 11/13 | 旧P-05 |
| D-22 | 店舗カード・店舗一覧では距離を表示せず、店舗の住所（store.address）を表示する | 11/13 | 旧P-06 |
| D-23 | MVPでは、注文状態を「2=期限切れ」に変える処理は作らない。注文状態の変更は 0→1（受け取り）だけ。order_status の「2=期限切れ」は定義だけ残し、作るときに使う | 11/13 | 旧P-07 |

## MVPでは使わないルール

|---|---|---|---|
