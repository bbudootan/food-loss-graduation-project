## v3の設計方針と採用技術

本プロジェクトのワイヤーフレーム制作では、Figmaやdraw.ioなどの作図ツールを使用せず、ASCIIテキストによる設計手法を採用しました。

限られた開発リソースの中で品質と効率を両立させるため、AIコーディングエージェントの活用を見据え、設計から実装への移行を円滑に進められる制作プロセスを重視しています。

### 採用理由

**1. コンピューターとの親和性が高い**

ASCIIテキストで記述したレイアウトは、コンピューターによる読み取りや編集が容易であり、SVG形式への変換や、HTML・CSSなどの実装コードへの展開にも活用できます。

特に、AIコーディングエージェントとの親和性が高く、設計段階で作成したテキストを実装時にも再利用しやすい点が大きなメリットです。これにより、設計段階での検討や改善に費やした時間を、実装工程の効率化につなげることができます。

また、今回は手描きのワイヤーフレームを作成する代わりに、GitHubで公開されているオープンソースツール「[Svgbob](https://ivanceras.github.io/svgbob-editor/)」を使用し、ASCIIテキストからSVG形式のベクター画像への変換を行いました。

この方法により、テキストベースでの編集のしやすさを維持しながら、拡大・縮小しても画質が劣化しないワイヤーフレーム画像を作成できます。

ただし、Svgbobで生成したSVGファイルは、draw.ioなどの作図ツールで個々の図形を直接編集することには適していません。そのため、ASCIIテキストを編集用の原本として管理し、必要に応じてSVGファイルを再生成する運用方針としています。

**2. 修正・反復にかかるコストが低い**

要素の追加や配置の変更は、テキストを編集するだけで短時間に対応できます。

一般的な作図ツールのように、図形を一つずつ移動したり、レイアウト全体を手作業で再構成したりする必要がないため、仕様変更や設計方針の見直しが頻繁に発生する開発初期段階に適しています。

また、GitHubによるバージョン管理と組み合わせることで、設計変更の履歴を記録しながら、複数のレイアウト案を効率的に比較・検討できます。

このように、試行錯誤を繰り返しやすく、設計と実装の両面で柔軟性を確保できることが、本手法を採用した主な理由です。

**3. 今回の修正で意識したこと**

特に大きく調整したのは、元の「SVGに変換すれば HTML・CSSにも簡単に直接変換できる」という印象を与えかねない部分です。

実際には、ASCIIからSVGへの変換と、ASCIIの設計情報をもとにAIがHTML/CSSを実装することは別の工程です。その違いが伝わるようにしました。

また、Svgbobで出力したSVGが絶対に編集できないわけではありません。SVG自体は編集可能な形式ですが、Svgbobが生成した図形をdraw.io上で個別の編集可能なオブジェクトとして扱うのは難しい、という表現のほうが技術的に正確です。

この文章なら、単に「AIを使って楽をした」という説明ではなく、なぜその技術を選び、どのように設計資料を管理するのかという開発上の判断を示せます。
