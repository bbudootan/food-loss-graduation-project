# 店舗運営者側 MVP 画面遷移図 v3

作成日：2026-11-16

最終更新日：2026-11-16

「注文キャンセル」機能の復活と操作フローの簡略化に伴う更新。

再度話し合った結果、MVPでは店舗運営者側の注文キャンセル機能を復活させることにした。

実際の在庫数とシステム上の在庫数が一致しない場合がある。例えば、商品が店頭で先に売れてしまい、店舗が受け付けた注文の商品を渡せなくなるケースが考えられる。そのため、注文処理の流れを成立させるために、必要最低限のキャンセル操作を残す。

また、開発工数と画面遷移の複雑さを減らすため、従来の独立した「キャンセル内容確認画面」は設けず、現在の画面上に表示するモーダル（確認ダイアログ）で操作を完結させる。

## 1. キャンセルの適用条件と業務ルール

- 注文をキャンセルできるのは、その注文を受けた店舗の運営者のみとする
- 対象は、未受取（`order_status = 0`）で、実際の在庫不足などにより商品を渡せない注文に限る
- キャンセル成功後、注文ステータスを `3 = キャンセル（店舗都合）` に更新する
- キャンセルは取り消せず、同じ注文を繰り返しキャンセルすることもできない
- MVPでは、キャンセル後の在庫の自動復元と、デモ決済に対する返金処理は実装しない
- （暫定）キャンセル理由を店舗運営者が手入力する必要はなく、あらかじめ設定した「店舗都合」という理由を使用する。`cancel_reason` カラムを残すかどうかは、最終的なDB仕様に合わせて決める

## 2. 画面操作・遷移フロー

### ① 注文詳細画面

店舗運営者が「注文キャンセル」ボタンをクリックする

### ② キャンセル確認モーダル

**現在の画面上に確認ダイアログを表示し、別のページには遷移しない**

表示メッセージ：「この注文をキャンセルしますか？キャンセル後は元に戻せません。」

操作ボタン：

- 「戻る」：モーダルを閉じ、注文詳細画面にとどまる。データの更新は行わない
- 「キャンセルする」：キャンセルを確定し、PHPでの処理を開始する

### ③ PHP処理

- 注文がログイン中の店舗に属しており、ステータスが「受取待ち」のままであることを確認する
- 注文ステータスとキャンセル日時を更新する
- （暫定）キャンセル理由は最終的な仕様に従って記録する
- 処理中は「処理中…」と表示し、二重送信を防ぐためにボタンを無効化する
- PHPの処理結果に応じて成功・失敗を判定する

### ④ 処理結果

処理が成功した場合：
```
現在の「注文詳細画面」に戻って表示を更新する
↓
注文ステータスを「キャンセル済み」と表示する
「注文キャンセル」ボタンを非表示または無効にする
緑色の成功メッセージ「注文をキャンセルしました」を表示する
```

処理が失敗した場合：
```
元の注文ステータスを維持し、キャンセル成功と誤って表示しない
赤色のエラーメッセージ「キャンセル処理に失敗しました」を表示する
```

処理成功を知らせる別のモーダルや、専用のキャンセル完了画面は設けない
