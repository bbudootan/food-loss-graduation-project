# DECISIONS（決めた業務ルール）

話し合って決めたルールを記録します。
テーブル定義書の変更は [CHANGELOG.md](CHANGELOG.md) を見てください。
関連は、Issue #3 のコメント番号（②など）です。

## 決定済み

| No | ルール | 決定日 | 関連 |
|---|---|---|---|
| D-01 | 注文明細には order_id・listing_id・quantity だけを持たせる。商品名・単価は 出品 → 商品マスター から取る。商品マスターを編集したら updated_date を記録し、注文日時より後に更新されていたら「商品情報が変更されています」と表示する | 10/28 | 先生のレビュー |
| D-02 | 注文が入った出品は価格を変更できない。値段を変えるときは新しく出品し直す | 11/03 | D-01 |
| D-03 | 注文はお店ごとに分ける（1注文＝1店舗）。注文明細を登録するときに、出品の店舗IDが注文の店舗IDと同じかをPHPで確認し、違っていたら ROLLBACK する | 11/03 | ⑤ |
| D-04 | 注文確定（注文・注文明細の登録、在庫を減らす、ポイント利用、デモ支払い）は1つのトランザクションで行う。デモ支払いに失敗したら全部 ROLLBACK して、注文は残さない | 11/03 | ④ ⑤ |
| D-05 | 受け取り時間帯：注文時刻（開店前なら開店時刻）から、「閉店時間」と「注文内でいちばん早い sale_end」の早いほうまでを30分刻みで選ぶ。受け取りの開始時刻は持たない。ユーザー側は「19:00まで受取可」のように表示する | 11/03 | [②](https://github.com/bbudootan/food-loss-graduation-project/issues/3#issuecomment-6579461412) |
| D-06 | listing.quantity は「今売れる残りの数」。注文確定時に `WHERE quantity >= 注文数` を付けて減らし、0件なら在庫不足として ROLLBACK する。未受け取りの数は注文明細から計算し、売り切れは quantity = 0 で判断する | 11/03 | ④ |
| D-07 | 注文状態の変更は 0→1（受け取り）、0→2（期限切れ）、0→3（取り消し）だけ。1・2・3からは変えない。更新は `WHERE order_status = 0` を付けて行い、更新件数が0件なら何もしない | 11/03 | ⑤ |
| D-08 | ポイント：注文確定時に used_point 分を減らす（POINT_REDEMPTION）。受け取り完了時に total_amount / 100 を付与する（PURCHASE_AWARD）。取り消し時は used_point を返す（POINT_REFUND）。状態の更新・履歴の追加・残高の更新は1つのトランザクションで行い、二重処理は D-07 の条件で防ぐ | 11/03 | ③ ⑤ |
| D-09 | point_history.change_reason は PURCHASE_AWARD・POINT_REDEMPTION・GAME_REWARD・POINT_REFUND・SUPPORT_DONATION の5種類だけ。ミニゲームの報酬は、その日の GAME_REWARD の件数をPHPで数えて1日2回まで | 11/03 | ③ |
| D-10 | 獲得予定ポイントは列を持たず、受け取り待ちの注文ごとに total_amount / 100（切り捨て）を計算して合計する | 11/03 | ③ |
| D-11 | レビューは店舗だけが対象で、注文1件につき1件。投稿者が注文した本人かはPHPで確認する | 11/03 | — |
| D-12 | デモ支払いなので「支払い待ち」の状態は作らない。payment_status は削除する | 11/03 | ⑤ |
| D-13 | 店舗ジャンル・定休日・店舗画像は、出店申請では入力せず、承認後に店舗情報画面で入力する | 10/29 | — |
