■2. 受け取り時間帯（②への回答）

・同じ店舗の注文はまとめて受け取るので、受け取り予定は注文テーブルの pickup_schedule に保存します
・出品テーブルには締め切り（sale_end）だけを持たせ、受け取りの開始時刻は持たせません
・選べる時間帯は、注文時刻（開店前なら開店時刻）から、「閉店時間」と「注文内の商品でいちばん早い sale_end」の早いほうまでです。30分刻みで選べるようにします

【ユーザー側へのお願い】
カート画面などで商品ごとに出している「18:00〜19:00」のような開始時刻は使えなくなります。「19:00まで受取可」のような表示にしてもらえると助かります。


■3. ポイント（③への回答）

3-1. トランザクション
注文状態の更新・ポイント履歴の追加・account.point_balance の更新は、1つのトランザクションで処理します。全部成功したら COMMIT、どこかで失敗したら ROLLBACK します。

3-2. 二重付与の防止
idempotency_key は追加せず、注文状態を条件にした更新で防ぎます。

　UPDATE orders SET order_status = 1, pickup_date = GETDATE()
　WHERE order_id = ? AND order_status = 0
　（受け取り待ちのときだけ更新する）

更新件数が1件のときだけポイントを付けます。0件ならすでに受け取り済みなので、何もしません。キャンセル時のポイント返還も同じ考え方です。
ミニゲームは、その日の GAME_REWARD の件数をPHPで数えて、1日2回までにします。

3-3. 獲得予定ポイント
列は追加せず、計算で出します。受け取り待ちの注文ごとに total_amount / 100（整数の割り算なので切り捨て）を計算して合計します。合計してから割るのではありません。

3-4. change_reason の値
列名は change_reason のままにして、入れられる値をCHECK制約で次の5つに決めました。

・PURCHASE_AWARD：購入で獲得（受け取り完了時）
・POINT_REDEMPTION：購入時に利用
・GAME_REWARD：ミニゲームの報酬
・POINT_REFUND：ポイント返還（キャンセル時）
・SUPPORT_DONATION：森づくりの応援で利用（マイページの「500ptで応援する」のために追加）


■4. 在庫数（④への回答）

・出品テーブルの quantity は「今売れる残りの数（販売可能な数）」です。10個のうち3個注文されたら7にします
・在庫は注文が確定した時点で減らします（受け取り時点で減らすと、売りすぎが起きるため）
・注文の確定（注文と注文明細の登録、在庫を減らす処理、ポイント利用）は1つのトランザクションで処理します

　UPDATE listing SET quantity = quantity - 2
　WHERE listing_id = ? AND quantity >= 2
　（在庫が足りるときだけ減らす）

更新件数が0件なら在庫不足なので、ROLLBACK して「売り切れました」と表示します。

・「未受け取りの数」は注文明細から計算し、「売り切れ」は quantity = 0 で判断します（列は追加しません）
・店舗都合でキャンセルしたときは在庫を戻し、期限切れのときは戻しません


■5. そのほかに決めたこと

・注文が入った出品は、価格を変更できません（値段を変えるときは新しく出品し直します）。注文明細に単価を持たないためです
・商品マスターを編集したら updated_date を記録します。注文日時がそれより前の注文には、「商品情報が変更されています」と表示します
